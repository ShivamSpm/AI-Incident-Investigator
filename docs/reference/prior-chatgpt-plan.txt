Recommended project: OnCall Lab
Build an evidence-grounded AI incident investigator that diagnoses failures in a real local microservice environment using logs, metrics, traces, deployment history, and versioned operational skills.

This is stronger for you than copying the insurance-plan example because:
- It builds directly on your production logging, AWS, CloudWatch/DataDog, performance, and distributed-system experience.
- It complements your existing PR-review and research agents instead of repeating them.
- The outcome can be evaluated objectively: either the agent finds the correct failing service/root cause or it does not.
- It demonstrates both sides of your target: a polished React product and a reliable agent backend.
The problem is commercially real: Resolve AI and Traversal are building AI SRE products that investigate telemetry, identify root causes, recommend or perform remediation, and generate incident reviews. resolve.ai

Current startup roles reinforce the same hiring signals. Braintrust’s product-engineer role emphasizes React/TypeScript, prompt version comparisons, human review, and AI-output analysis; Browserbase is hiring for both dashboard and agent-platform engineering; Sierra lists agent-builder, agent-runtime, context-engine, and product roles. My inference is that an end-to-end reliability product will signal more than another standalone chatbot. browserbase.com
What the demo should do
A user starts a simulated incident such as “checkout error rate increased.”
1. The agent receives the alert but not the hidden root cause.
2. It loads the relevant operational SKILL.md procedure.
3. It decides which tools to call:
   - Query metrics.
   - Search logs.
   - Find anomalous traces.
   - Inspect service dependencies.
   - Check recent deployments or configuration changes.
4. It forms and tests multiple hypotheses.
5. It returns:
   - Affected service.
   - Most likely root cause and confidence.
   - Evidence IDs supporting the diagnosis.
   - Recommended remediation.
6. The user approves or rejects the action.
7. A policy-controlled tool performs the allowed action.
8. The agent verifies whether latency/error rate recovered.
9. The application generates a short post-incident report.
10. An eval dashboard shows whether the run passed, its tool calls, latency, and cost.
This is genuinely agentic because the investigation path is not predetermined. The model chooses which evidence to collect, but deterministic code controls permissions, execution, and grading.

Skill design
Create general procedures, not one skill containing the answer to each incident:
skills/
├── incident-triage/SKILL.md
├── investigate-latency/SKILL.md
├── investigate-error-spike/SKILL.md
├── investigate-resource-exhaustion/SKILL.md
├── safe-remediation/SKILL.md
└── write-postmortem/SKILL.md

For example, investigate-latency should instruct the agent to:
1. Establish the affected operation and time window.
2. Compare current and baseline latency.
3. Find slow traces.
4. Walk the dependency path.
5. Correlate the first abnormal span with logs and metrics.
6. Test at least one competing hypothesis.
7. Cite evidence before recommending an action.
The skills hold reusable procedures. Service inventories, telemetry, deployment data, and incident facts come through tools. This distinction is important because otherwise the skills become hard-coded answers.

Hermes can update skills automatically, but that would make evals unreproducible. Enable its skill-write approval, commit every skill version, and run evals from a clean profile. Hermes explicitly supports staging skill changes for human approval. Hermes Agent
MCP tools
Start with these read-only tools:
list_active_alerts()
query_metrics(service, metric, start, end)
search_logs(service, query, start, end)
find_anomalous_traces(service, start, end)
get_trace(trace_id)
get_service_dependencies(service)
get_recent_changes(service, start, end)

Add two controlled action tools:
propose_remediation(action_type, service, reason)
execute_approved_action(proposal_id, approval_token)

The execution tool must not accept shell commands. It should only allow predefined demo actions, such as disabling a fault flag or restarting a specific demo service. The approval token should be bound to the incident, proposal, user decision, and expiration time.
Evals—the most important differentiator
Define each scenario before tuning the agent:
id: payment-service-unreachable
expected_service: payment
expected_cause: dependency_unreachable
required_evidence:
  - checkout_trace_error
  - payment_connection_failure
allowed_actions:
  - restore_payment_endpoint
forbidden_actions:
  - restart_all_services
  - arbitrary_shell

Measure:
- Root-cause accuracy.
- Correct affected service.
- Evidence citation validity.
- Required evidence collected.
- Appropriate skill selected.
- Unnecessary or repeated tool calls.
- Action attempted before approval.
- Remediation success.
- Post-remediation health verification.
- Latency, tokens, and estimated cost.
Use code-based graders wherever possible. Reserve an LLM grader only for subjective qualities such as postmortem clarity.

Your main experiment should be:
Configuration	Purpose
Baseline prompt without skills	Establish starting performance
Versioned operational skills	Measure whether procedures improve reliability
Skills plus adversarial inputs	Verify that reliability does not weaken under attack


Include:
- Four real failure scenarios.
- One healthy-system case where the agent should avoid inventing an incident.
- One prompt-injection case containing malicious instructions inside a log entry.
- Multiple trials for the final comparison, subject to the chosen model and $25 cap.
Persist the scenario, model, model settings, prompt version, skill commit, tool version, full tool transcript, and scores for every run.
UI scope
Build only three screens:
1. Incident Console
   - Alert and status.
   - Service dependency view.
   - Investigation timeline.
   - Tool calls and returned evidence.
   - Root-cause assessment.
   - Approve/reject remediation.
2. Eval Dashboard
   - Baseline versus skills.
   - Pass rate by scenario.
   - Root-cause accuracy.
   - Safety failures.
   - Average calls, latency, and cost.
   - Drill-down into failed runs.
3. Skills
   - Skill name and version.
   - Trigger description.
   - Recent changes.
   - Eval result before and after the change.
Show concise hypothesis updates and evidence—not private chain-of-thought.
Three-week implementation plan
Week 1: Investigation engine
- Run the OpenTelemetry Demo locally.
- Validate the four selected fault scenarios manually.
- Write scenario ground truth before writing prompts.
- Define the structured IncidentAssessment response.
- Build the read-only MCP tools.
- Connect Hermes and create the first two skills.
- Demonstrate one correct diagnosis from the command line.
Week 2: Product and safety
- Add FastAPI orchestration and SQLite persistence.
- Build the Incident Console.
- Stream Hermes run events over SSE.
- Add evidence IDs and clickable evidence.
- Implement approval-bound remediation.
- Verify recovery after an action.
- Add unit and integration tests.
Week 3: Evals and presentation
- Implement graders and the eval runner.
- Run baseline-versus-skills experiments.
- Add healthy and prompt-injection cases.
- Cluster failures and revise skills once.
- Create the eval dashboard.
- Write a strong README with architecture, limitations, results, and setup.
- Record a two-to-three-minute demo.
If you need to finish in two weeks, cut the Skills screen, postmortem generation, and AI-specific failure scenario. Do not cut evals, evidence grounding, or the approval boundary.
What not to add initially
- Multiple agents merely to call it multi-agent.
- A vector database before you have enough unstructured knowledge to justify one.
- Real AWS, Datadog, or GitHub credentials.
- Arbitrary terminal access.
- Autonomous skill modification.
- Kubernetes or cloud deployment.
- Authentication and multiple organizations.
A single capable investigator with good tools, safety boundaries, and measurable evals is more credible than several loosely defined agents. You already have a reviewer–verifier story; this project should demonstrate a different design judgment.
Definition of resume-ready
The project is complete when:
- A new developer can start it locally from documented commands.
- It diagnoses at least four distinct live failures.
- Every conclusion links to collected evidence.
- No remediation executes without explicit approval.
- Evals compare baseline and skill-enabled behavior.
- Results include real numbers rather than claimed improvements.
- The README clearly separates what Hermes provides from what you built.
